### **Hotelio Booking Service - Полный цикл миграции и развертывания**

## Обзор

Репозиторий содержит реализацию миграции сервиса бронирования из монолитной архитектуры Hotelio в микросервисную с полным циклом CI/CD и управлением трафиком через Istio Service Mesh.

## Контекст

Hotelio — онлайн-платформа для бронирования отелей и апартаментов. Компания переходит от монолитного Java-приложения к микросервисной архитектуре для решения проблем масштабируемости, независимой разработки и отказоустойчивости.

## Архитектура

### Миграция с монолита

Анализ текущей архитектуры и стратегия перехода по паттерну Strangler Fig:

- *Целевое состояние*: Полностью микросервисная архитектура с API Gateway, отдельными БД для каждого сервиса и независимыми CI/CD
- *Первый модуль:* `BookingService` выбран как центральный бизнес-компонент с четкими границами
- *Стратегия:* Поэтапное выделение сервисов с сохранением работоспособности системы

### Миграция данных

Выделение логики бронирования в отдельный `booking-service` с gRPC-интерфейсом и отдельной базой данных.

*Стратегия*: Двойная запись + асинхронный backfill

- Новые бронирования записываются как в монолит, так и в booking-service
- Исторические данные синхронизируются асинхронно
- Обеспечивается нулевой даунтайм и контроль целостности данных

### Федеративный GraphQL API

Реализация GraphQL Federation для объединения данных из разных сервисов:

- Gateway (порт 4000): Единая точка входа для клиентов
- Booking-subgraph (порт 4001): Интеграция с `booking-service` через gRPC, реализация ACL
- Hotel-subgraph (порт 4002): Интеграция с монолитом через REST

### CI/CD и Kubernetes

- Helm-чарты для `booking-service`
- CI/CD pipeline с использованием GitLab CI
- Развертывание в Minikube с Docker-образами
- Service Discovery через DNS

### Управление трафиком с Istio

- Canary-релиз: 90% трафика на v1, 10% на v2
- Маршрутизация по фича-флагу: при `X-Feature-Enabled`: true → v2
- Fallback: автоматический переход при ошибках
- Retry и Circuit Breaking: защита от падений сервисов
